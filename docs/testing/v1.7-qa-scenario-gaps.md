## GAP-01 — sharpe_ratio_trade_method present in POST /validate/calculations response

**Acceptance criterion:** `POST /validate/calculations` response includes the field
`sharpe_ratio_trade_method` in its validated metrics output.
**Derived from:** `analytics_endpoints.md` — validated metrics contract; v1.7 verification gap 1.
**Type:** Backend

**Setup:**
Staging environment running. At least one closed trade with P&L data in the staging database.

**Steps:**
1. Call `POST /validate/calculations` with a valid request body (use any complete payload
   that the endpoint accepts — refer to `analytics_endpoints.md` for the schema).
2. Inspect the response body.
3. Locate the validated metrics section of the response.

**Expected result:**
- HTTP 200
- Response contains `sharpe_ratio_trade_method` as a field in the validated metrics output
- The field value is a float or `null` (not absent)
- Field name matches exactly: `sharpe_ratio_trade_method` (no aliases, no camelCase variant)

**Notes:**
This field was added during the v1.7 spec debt resolution (EPIC-06). Its presence confirms
the endpoint returns the full validated metric set and the spec is enforced.

## GAP-02 — POST /validate/calculations returns all 14 validated metrics

**Acceptance criterion:** `POST /validate/calculations` response contains exactly 14 validated
metric fields in its output (per `analytics_endpoints.md` validated metrics contract).
**Derived from:** `analytics_endpoints.md` — validated metrics count; v1.7 verification gap 1.
**Type:** Backend

**Setup:**
Same as GAP-01.

**Steps:**
1. Call `POST /validate/calculations` with a valid complete payload.
2. Inspect the response body.
3. Count the number of distinct metric fields returned in the validated section.

**Expected result:**
- HTTP 200
- Exactly 14 metric fields are present in the validated output
- `sharpe_ratio_trade_method` is one of the 14 (confirmed by GAP-01)
- No fields are missing; no extra undocumented fields are present beyond the 14

**Notes:**
The 14-metric count is per `analytics_endpoints.md`. If the endpoint returns a different count,
raise with Head of Specs Team — the spec or implementation is diverged. Do not pass this
scenario if the count differs.

## GAP-03 — GET /portfolio response fields match portfolio_endpoints.md v1.9.0 contract

**Acceptance criterion:** `GET /portfolio` response `data` object contains all fields defined
in `portfolio_endpoints.md` v1.9.0 at the portfolio level and at the position level.
**Derived from:** `portfolio_endpoints.md` v1.9.0 §GET /portfolio; v1.7 verification gap 2.
**Type:** Backend

**Setup:**
Staging environment running. Portfolio with at least one open position.

**Steps:**
1. Call `GET /portfolio` on the staging API.
2. Inspect `data` (portfolio-level fields).
3. Inspect `data.positions[0]` (position-level fields — use first position if multiple exist).
4. Cross-reference against `portfolio_endpoints.md` v1.9.0 field list for both levels.

**Expected result:**

Portfolio-level `data` must contain all of:
`cash`, `cash_balance`, `total_value`, `open_positions_value`, `total_pnl`, `initial_value`,
`net_deposits`, `live_fx_rate`, `last_updated`, `current_drawdown_percent`,
`peak_portfolio_value`, `portfolio_heat_percent`, `position_risks`, `positions`

Position-level `data.positions[n]` must contain all of:
`id`, `ticker`, `market`, `entry_date`, `entry_price`, `shares`, `current_price`,
`current_value`, `pnl`, `pnl_pct`, `current_stop`, `holding_days`, `status`,
`display_status`, `fx_rate`, `grace_period`, `grace_days_remaining`, `live_fx_rate`

- All field names match exactly (snake_case; no aliases)
- No required field is absent
- HTTP 200 with `status: "ok"`

**Notes:**
This is a field-alignment check — values do not need to be validated here (that is covered
by existing QWB scenarios and ST-05 integration tests). Focus on presence and naming only.

## GAP-04 — GET /trades response includes holding_days field

**Acceptance criterion:** `GET /trades` response includes `holding_days` as a field on each
trade record returned.
**Derived from:** `trade_endpoints.md` — GET /trades field contract; v1.7 verification gap 3.
**Type:** Backend

**Setup:**
Staging environment running. At least one closed trade in the staging database.

**Steps:**
1. Call `GET /trades` on the staging API (no filters required — default response).
2. Inspect the first trade record in the response array.
3. Confirm `holding_days` is present.

**Expected result:**
- HTTP 200
- Each trade record in the response contains `holding_days` as a field
- `holding_days` is an integer (number of calendar days between `entry_date` and `exit_date`)
- Field is present on all trade records — not only conditionally included

**Notes:**
`holding_days` was specified in `trade_endpoints.md` but was found missing from the live API
response during v1.7 verification. Confirm both that the field is present and that the value
is plausible (e.g., a trade entered 2026-01-01 and exited 2026-01-15 should show 14).
