# Idea: Design Token System

## 1. Problem Statement

UI colours, typography, and spacing are implemented ad hoc across the frontend. There is no design token system — no canonical set of named values for primary colour, danger colour, success colour, body text size, heading sizes, and spacing units. The result is that visual consistency depends entirely on individual engineering implementation choices: a "danger" state in the positions table may use a different red than a "danger" state in the sizing calculator widget, because there is no canonical `--color-danger` token that both reference. Any design-wide change (for example, adjusting the primary colour for accessibility reasons) requires hunting down every hardcoded value across the codebase.

## 2. Strategic Alignment

Section reference: Frontend Specs §4 — Information architecture ("the specs structure scales without monoliths; separates intent from implementation")

Alignment rationale: A design token system is the application of the same principle — separating intent (the design language) from implementation (the specific colour values) — to the UI layer. Just as canonical specs separate what the system does from how it is implemented, design tokens separate what the UI should look like from how individual components render it. This is the UX parallel to the canonical specification governance model.

## 3. Proposed Solution

Define a minimal design token set in `docs/ux/design_tokens.md` and as CSS custom properties in a canonical stylesheet: `--color-primary`, `--color-danger`, `--color-success`, `--color-warning`, `--color-text`, `--color-background`, `--spacing-unit`, `--font-size-body`, `--font-size-heading`. Apply these tokens to all frontend components, replacing hardcoded values. The document is the canonical source; the stylesheet is the implementation. Any colour or typography change is made in one place and propagates everywhere.

## 4. Expected Value

Eliminates visual inconsistency caused by hardcoded values. Enables theme-wide changes (accessibility contrast adjustments, branding updates) without individual component edits. Foundation for future dark mode support if needed. Measurable as: reduction in visual inconsistency defects (different "danger" colours in different components) to zero after implementation.

## 5. Effort Estimate

- [x] Medium — 1–3 weeks

Constraints or dependencies: Requires an audit of existing hardcoded colour and typography values across the frontend to replace them with token references. The Base44 frontend framework must support CSS custom properties.

## 6. Reversibility

- [x] Mostly reversible — minor rework required

Reasoning: Reverting token-referenced values requires replacing them with hardcoded values again — low effort but non-zero.

Reasoning: High leverage for visual consistency but requires a codebase-wide refactor of hardcoded values. Should be prioritised after any active accessibility work, as accessibility requirements may change the token values themselves.
