# Idea: User-Facing Error Message Mapping Layer

## 1. Problem Statement

API error messages from the backend are sometimes displayed directly to the user, including technical strings such as `{"detail": "invalid value for field 'shares': must be > 0"}` or HTTP status code language. These messages are technically accurate but not user-friendly: a trader managing positions does not benefit from seeing raw validation error text, and in some cases raw error messages expose internal field names or implementation details. There is no canonical mapping from API error codes to user-facing messages that the frontend consistently applies.

## 2. Strategic Alignment

Section reference: Backend Engineering Patterns §7 — Response Envelope ("error responses use the detail field") and §4.1.7 — "an inline plain-language message is shown beneath the widget"

Alignment rationale: The canonical spec for the sizing calculator already requires "an inline plain-language message" for invalid results. This establishes the principle that system-level errors should be translated to plain language before display. Extending this to all error responses is applying the same standard consistently across the UI — which is what the frontend spec ownership role exists to do.

## 3. Proposed Solution

Create a frontend error mapping module: a lookup table that maps HTTP status codes and known API error codes/patterns to user-friendly message strings. Examples: HTTP 400 with "must be > 0" → "Please enter a value greater than zero"; HTTP 500 → "Something went wrong — please try again. If the problem persists, contact support." Apply this mapping to all error responses before display. No technical strings appear in the UI after implementation. Document the mapping in `docs/specs/frontend/error_messages.md`.

## 4. Expected Value

Eliminates user-visible technical error strings. Improves user confidence and reduces support enquiries caused by confusing error messages. Measurable as: proportion of API error responses displayed in plain language (target: 100%). Secondary: reduction in support reports citing confusing error messages.

## 5. Effort Estimate

- [x] Small — days to 1 week

Constraints or dependencies: Requires an audit of all current error display paths in the frontend. The error mapping must be maintained as the API evolves — requires a process for updating the mapping when new error codes are introduced.

## 6. Reversibility

- [x] Fully reversible — no lasting effects

Reasoning: The mapping is a translation layer; removing it reverts to displaying raw API errors.
