# Idea: Loading State Standardisation Across All API-Backed Interactions

## 1. Problem Statement

API calls from the frontend do not follow a consistent loading state pattern. The Position Sizing Calculator (§4.1.7) correctly specifies a loading state during the debounce-to-response window — but other API-backed interactions (position entry submission, trade exit, portfolio value update) have inconsistent or absent loading indicators. Users who click a button and see no feedback may click again, causing duplicate submissions. A double-submitted position entry or exit creates incorrect records in the trading database that require manual correction.

## 2. Strategic Alignment

Section reference: §4.1.7 — User interface interaction requirement ("a loading state is shown during the window between the debounce firing and the response returning")

Alignment rationale: The canonical spec already requires a loading state for the sizing calculator. Extending this pattern to all API-backed interactions applies the same principle consistently — the spec's intent is that the user always knows the system is processing their action. Inconsistent loading states mean the spec's safety property (user knows when to wait versus when to retry) applies only to one feature instead of the whole UI.

## 3. Proposed Solution

Define a canonical loading state pattern: (1) on form submission — disable the submit button, show an inline spinner, re-enable after response; (2) on data loads — show a skeleton screen in place of loading data; (3) on action buttons (exit position, update stop) — show a button-level loading state. Apply this pattern to all existing API-backed interactions. Document the pattern in `docs/specs/frontend/loading_states.md` as the canonical interaction standard.

## 4. Expected Value

Eliminates duplicate submissions caused by the user not knowing their action was processed. Reduces user confusion during slow network conditions. Measurable as: number of duplicate submission incidents per month (target: zero after implementation). Secondary: reduction in user-reported "I clicked it twice" support issues.

## 5. Effort Estimate

## 6. Reversibility

Reasoning: UI interaction patterns are reversible; removing a loading state reverts to current behaviour.
