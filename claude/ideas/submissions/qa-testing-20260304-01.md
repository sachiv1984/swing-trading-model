# Idea: Canonical Test Scenario Library

## 1. Problem Statement

Test scenarios for the system's critical behaviours — trailing stop calculation across all position states, grace period enforcement, market regime override, position sizing calculator constraints — exist implicitly in the QA team's knowledge but are not documented in a canonical, reusable format. When a new release is tested, scenarios are reconstructed from memory or previous verification reports. This creates inconsistency between releases, knowledge loss risk when a QA team member is unavailable, and no systematic way to verify that every critical behaviour is tested each cycle.

## 2. Strategic Alignment

Section reference: Director of Quality §4.2 — "ensure acceptance criteria are derived directly from canonical specifications; ensure regression coverage aligns with documented system behaviour"

Alignment rationale: A test scenario library is the canonical implementation of the Director of Quality's requirement that acceptance criteria derive from specifications and that regression coverage aligns with documented behaviour. Without it, coverage claims ("we tested the grace period") cannot be verified as systematic — they may be true or they may reflect what the tester happened to think of on the day. The library makes coverage claims auditable.

## 3. Proposed Solution

Create `docs/team_skills/quality/test_scenario_library.md` — a Class 1 canonical document structured by feature area. For each critical behaviour (grace period: stop is calculated but not enforced; trailing stop: stop moves up but never down; profit-aware stop: tight multiplier applied when P&L > 0), define: (1) the canonical spec section being tested, (2) the test setup (input state), (3) the expected outcome derived from the spec, and (4) the test type (automated or manual). The library is maintained by the QA & Testing Owner and reviewed with each spec change.

## 4. Expected Value

Ensures every critical behaviour is tested consistently across releases. Eliminates knowledge loss risk — any QA tester can execute the full scenario library from the document alone. Enables systematic regression coverage claims. Target: 100% of critical spec-defined behaviours have at least one documented test scenario within two cycles of adoption.

## 5. Effort Estimate

- [x] Medium — 1–3 weeks

Constraints or dependencies: Requires collaboration with the Strategy Owner and Metrics Analytics Owner to identify the full list of critical behaviours to cover. Should be developed alongside the spec-to-test traceability matrix (submitted by the Director of Quality).

## 6. Reversibility

- [x] Fully reversible — no lasting effects

Reasoning: A reference document; no technical lock-in.

## 7. What Would You Stop?

If this is prioritised, I would defer creating additional ad-hoc test scripts until the scenario library defines the canonical set of what needs testing. Building to a known inventory is more efficient than building ad hoc and auditing later.

## 8. Submitter Recommendation

- [x] Now — should be in the next roadmap cycle

Reasoning: Without this, every release tests whatever the current QA tester remembers to test. The system deserves deterministic test coverage, especially for calculation-critical behaviours.
