# Idea: Canonical Test Execution Report Template

## 1. Problem Statement

Verification reports written by the QA Lead across releases do not follow a canonical format. Each report is structured according to the judgement of the author at the time, meaning that: scope coverage is described differently between reports, the sign-off block varies in structure, and finding a specific piece of sign-off evidence (e.g., "was the grace period test executed for v1.6?") requires reading the full report rather than navigating to a standard section. For a governance-driven quality programme, inconsistent report formats undermine the auditability of sign-off evidence.

## 2. Strategic Alignment

Section reference: Director of Quality §4.4 — "ensure testing execution aligns with approved strategy; ensure defect management follows defect_lifecycle.md; ensure release readiness assessments are evidence-based"

Alignment rationale: Evidence-based release readiness assessments require that evidence is presented in a consistent, findable format. A template enforces the minimum required content — scope, scenarios executed, pass/fail summary, defects found, sign-off — and ensures every verification report can be reviewed and audited against the same structure. Without a template, evidence-based review is possible but inconsistent.

## 3. Proposed Solution

Create `docs/team_skills/quality/test_execution_report_template.md` — a Class 2 supporting document defining the canonical structure for all verification reports: (1) header (release, date, scope), (2) test scenarios executed (linked to the scenario library), (3) results summary table (scenario, expected, actual, pass/fail), (4) defects found (IDs, severity, resolution status), (5) sign-off block (QA Lead sign-off, Director of Quality sign-off, date). All future verification reports use this template.

## 4. Expected Value

Reduces report preparation time by providing a reusable structure. Makes sign-off evidence consistently findable across releases. Enables quality trend analysis across cycles (e.g., "how many defects were found in each release?"). Measurable as: proportion of verification reports complying with the template (target: 100% after adoption).
