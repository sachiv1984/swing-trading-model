# Idea: System Health Check Playbook

## 1. Problem Statement

There is no documented set of health checks that should be run after a production deployment or on a regular operational cadence. After deploying, the current practice is informal: someone checks whether the dashboard loads. Whether the database is connected, whether the calculation API is returning valid results, and whether background jobs are running correctly is not systematically verified. Degraded state (e.g., stale stop calculations due to a failed background job) could persist for days before a user notices.

## 2. Strategic Alignment

Section reference: Infrastructure & Operations Owner §2 — "monitoring and alerting playbooks" and "operational runbooks"

Alignment rationale: The role's mandate includes monitoring and alerting playbooks as a primary deliverable. A health check playbook is the operational procedure that makes monitoring actionable — it defines what to check, what a healthy state looks like, and what to do when it is not healthy. Without it, monitoring is a passive observer rather than an active control.

## 3. Proposed Solution

Create `docs/ops/runbooks/health_check_playbook.md` — a Class 3 operational document defining: (1) the list of endpoints and checks to run (GET /portfolio/positions, POST /validate/calculations, database connectivity), (2) the expected response time and content for a healthy state, (3) the procedure when a check fails (who to notify, what to escalate, what constitutes a severity-1 incident), and (4) the frequency for post-deployment checks (immediate) versus routine checks (daily automated).

## 4. Expected Value

Reduces mean time to detect (MTTD) for production health issues from "until a user notices" to within one check cycle. Provides a reproducible audit trail that health was verified after each deployment. Expected to catch silent failures — stale calculations, broken database connections — that the current informal process would miss.

## 5. Effort Estimate

- [x] Small — days to 1 week

Constraints or dependencies: Should be developed alongside the production deployment runbook to ensure the post-deployment validation steps are consistent between the two documents.
