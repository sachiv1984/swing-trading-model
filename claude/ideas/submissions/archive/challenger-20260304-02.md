# Idea: Define and Document the Unavailability Failure Mode

## 1. Problem Statement

The system generates exit recommendations that "require manual confirmation" (§8.1). This is correct and intentional. However, there is no documented behaviour for what happens if the user is unavailable for 24–48 hours when a recommendation fires. The position continues to be held past its stop with no system-level escalation, no documented user procedure, and no contingency. This is not a hypothetical: weekends, travel, illness, and connectivity failures are all real scenarios for an active trader. The human-in-the-loop model is correct, but its failure mode when the human is unreachable is unaddressed.

## 2. Strategic Alignment

Section reference: §3 — Human-in-the-loop execution model; §13.2 — "This system is not: an automated trading bot or a broker execution engine"

Alignment rationale: The Challenger exists to expose risk and force explicit trade-offs. The unavailability failure mode is a risk that the current governance model has not addressed explicitly. Section 3 correctly places the human in the loop; section 13 correctly excludes automation. Neither section addresses what the human should do when they cannot be in the loop. This is a documented gap in system boundaries, not a request to change the architecture.

## 3. Proposed Solution

Define an explicit policy (not a system feature) for user unavailability scenarios. This could be as simple as: a documented user instruction in the operational guide stating "before any period of unavailability exceeding 24 hours, the user should set a hard manual stop at the broker for each open position at the current system stop level." The policy is documented as a system boundary clarification in §13 or as an operational guide entry. The system itself does not change.

## 4. Expected Value

Removes an undocumented risk. Prevents the scenario where a position is held well past its stop because the user was unreachable — a scenario that could result in a loss significantly larger than the stop-based maximum. The policy costs nothing to define; the cost of the undocumented failure mode is a real financial exposure in every period of user unavailability.
