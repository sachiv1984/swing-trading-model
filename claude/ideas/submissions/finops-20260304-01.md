# Idea: Cloud Resource Tagging Standard

## 1. Problem Statement

Currently there are no mandatory tags on cloud infrastructure resources. It is impossible to attribute cloud costs to specific product features, environments, or development cycles. Any cost optimisation effort must start with a time-consuming manual audit to determine what each resource is for. If a runaway CI job or unexpected data egress event drives up costs, there is no automated way to trace which feature or workflow is responsible. Visibility is the prerequisite for all cost governance and it does not currently exist.

## 2. Strategic Alignment

Section reference: FinOps §4.1 — Cost Visibility & Attribution ("ensure cloud and infrastructure costs are traceable; prevent 'unowned' or opaque spend")

Alignment rationale: The FinOps guiding principle is "visibility precedes optimisation." A resource tagging standard is the foundational cost visibility mechanism — without it, all downstream cost reporting, budget alerting, and optimisation work is either impossible or unreliable. This is the required first step before any cost governance programme can function.

## 3. Proposed Solution

Define and document a mandatory tagging standard in `docs/ops/cloud_resource_tagging.md`: required tags are `{product: "trading-model", environment: "prod|dev|ci", feature: "backend|database|frontend|monitoring", owner: "<role-slug>"}`. Apply the standard to all existing cloud resources retroactively within one sprint. Enforce via infrastructure-as-code policy so new resources created without required tags fail the provisioning step. Document the standard as a Class 1 operational document.

## 4. Expected Value

Enables per-feature cost attribution within the first reporting cycle after implementation. Reduces time to identify a cost spike from "next monthly invoice" to "same day" via tagged cost explorer queries. Provides the data foundation for all future cost optimisation work. No optimisation possible without this baseline.

## 5. Effort Estimate

- [x] Small — days to 1 week

Constraints or dependencies: Requires agreement on the tag schema (straightforward) and access to the cloud provider's resource tagging API. Retroactive tagging of existing resources requires a one-time sweep.

## 6. Reversibility

- [x] Fully reversible — no lasting effects

Reasoning: Tags are metadata; removing them has no effect on resource function.

## 7. What Would You Stop?

No view — leave to debate. Tagging is infrastructure housekeeping; it does not compete with product delivery.

## 8. Submitter Recommendation

- [x] Now — should be in the next roadmap cycle

Reasoning: Every resource provisioned without tags after this window is a cost attribution gap. The sooner the standard is defined, the smaller the retroactive remediation effort.
