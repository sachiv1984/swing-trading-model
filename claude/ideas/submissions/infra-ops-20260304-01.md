# Idea: Production Deployment Runbook

## 1. Problem Statement

There is no documented step-by-step production deployment procedure. Deployments rely on tribal knowledge held by the person who most recently deployed. If that person is unavailable — due to illness, holiday, or role change — a deployment could be performed incorrectly, skipping validation steps or missing rollback procedures. In a trading system where incorrect data or a broken API causes a user to miss a stop recommendation, deployment correctness is not a nice-to-have.

## 2. Strategic Alignment

Section reference: Infrastructure & Operations Owner §2 — "deployment and release guides" are a core operational responsibility

Alignment rationale: The role's mandate explicitly lists deployment guides as a primary deliverable. The absence of a production deployment runbook is a gap in the core scope of this role. Creating it is not an optional improvement — it is fulfilling the stated responsibility.

## 3. Proposed Solution

Create `docs/ops/runbooks/production_deployment.md` — a Class 3 operational document covering: (1) pre-deployment checklist (branch verified, PR merged, CI green, DB migration applied if needed), (2) deployment steps in order, (3) post-deployment validation (key endpoints responding, database connectivity confirmed, a known calculation returning the expected value), (4) rollback procedure if validation fails, and (5) escalation path if rollback is needed. The document is reviewed and tested by a second person each release.

## 4. Expected Value

Reduces deployment risk: any team member can deploy safely without the primary deployer present. Provides an audit trail demonstrating that deployment was performed correctly. Expected to reduce deployment incidents caused by missed steps from their current unknown rate to near-zero.

## 5. Effort Estimate

- [x] Small — days to 1 week

Constraints or dependencies: Requires the primary deployer to document their current process before it is formalised. Should include a test run where a second person executes the runbook to verify completeness.

## 6. Reversibility

- [x] Fully reversible — no lasting effects

Reasoning: A runbook document can be archived at any time with no system impact.

Reasoning: The next production deployment will happen without a runbook unless this is done. Given v1.7 has just shipped, the deployment process is fresh in memory — now is the ideal moment to document it.
