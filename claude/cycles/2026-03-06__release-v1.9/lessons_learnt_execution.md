### Friction Item 1

**Classification:** Type C — Dependency Stall: The same governance file was modified independently on parallel EPIC branches, creating a cascading merge conflict chain.

**Recurrence:** No — prior cycle had no parallel EPIC branches modifying the same file simultaneously.

**What happened:**
`execution_state.json` (the per-sprint progress tracker) is written by the engine during execution. In this sprint, EPIC-04 and EPIC-05 were delivered on separate branches running in parallel. Both branches modified `execution_state.json` independently. When EPIC-04 was merged to main first, EPIC-05's PR immediately showed a merge conflict on `execution_state.json`. After resolving that conflict and pushing, a second CI run was needed. The engine then had to resolve a further conflict after the merge commit updated main again. This required three rounds of conflict resolution and three CI runs for EPIC-05 before it could be merged, adding ~45 minutes of latency.

**Where in the routine:** STEP 4 — Merge Gate; PR merge coordination between parallel EPIC branches.

**Root cause:** Process gap — `execution_state.json` is a shared governance file but is modified on feature branches as if it were a per-EPIC artefact. There is no convention for how to sequence execution_state.json writes when multiple EPIC branches are active simultaneously.

**Blast radius analysis:**
- What would have propagated: Every sprint with more than one active EPIC branch faces the same conflict pattern. The number of conflict resolution rounds equals (n-1) where n is the number of parallel EPIC branches. A 4-EPIC sprint would require 3 conflict resolution cycles.
- When it would have surfaced: At every PR merge where more than one EPIC branch was active — next sprint.
- Recovery cost if uncaught: Low per occurrence (conflict resolution is quick) but cumulative — each conflict round requires a CI run (~3–5 minutes). For a 4-EPIC sprint with 3 conflict rounds plus retries, this could add 30–60 minutes of CI time per sprint close.

**Process patch:**

→ Deferred patch (cannot apply this run — process convention document is outside execution engine write scope):
  - File: `claude/system/shared_standards.md`
  - Section: New §12 — Parallel EPIC Branch Merge Sequencing
  - Change required: Add a convention: when multiple EPIC branches are active, the execution engine should merge them in dependency order (or alphabetical if no dependency) and update `execution_state.json` on main directly via a GOVERNANCE commit after each EPIC merge, rather than including execution_state.json in the EPIC branch. Alternatively: designate execution_state.json as "merge using --ours from the more recent branch (the EPIC with the later completion timestamp)". Document the expected conflict pattern and the resolution rule so it is not discovered ad-hoc at merge time.
  - Owner: Head of Specs Team
  - Target: Before next sprint with more than one parallel EPIC branch (2026-03-06__release-v1.9 Sprint 2)

### Friction Item 2

**Classification:** Type B — Semantic Mismatch: A component's user-visible string was changed in one EPIC's branch, breaking a Playwright test in an adjacent EPIC's branch that expected the original string.

**Recurrence:** No — first sprint with Playwright acceptance tests active in CI.

**What happened:**
EPIC-04 commit `20e688f` changed the GracePeriodPanel empty state message from `"No positions in grace period."` to `"No positions currently in grace period."` (adding the word "currently"). The ST-11 Playwright test (EPIC-05 branch, SC-RD-25) had been written against the original component text and expected `text=No positions in grace period`. After EPIC-04 merged into main and EPIC-05 was rebased/updated, the test failed with "element(s) not found". The fix (updating the test locator to include "currently") was straightforward but required an additional commit and CI run.

**Where in the routine:** STEP 4 — Merge Gate for EPIC-05; post-merge CI failure triggered by cross-EPIC component string change.

**Root cause:** Naming inconsistency / missing artefact — the Playwright test was written against a specific UI string with no reference to a canonical spec definition for that string. UI microcopy (empty state messages) is not defined in the spec (risk_dashboard.md) — the spec defines the behaviour ("display empty state") but not the exact text. This creates a gap where a frontend implementer can change the text without the test author knowing to update the test.

**Blast radius analysis:**
- What would have propagated: Any future EPIC that modifies a UI string tested by an existing Playwright scenario will cause the same break. As the Playwright test suite grows (17 tests now, more in Sprint 2), the number of potentially breakable string assertions grows proportionally.
- When it would have surfaced: At EPIC merge gate — detectable immediately by CI, but only after the conflict is introduced. No pre-merge warning is possible with the current tooling.
- Recovery cost if uncaught: Low per occurrence (test fix is trivial). Moderate governance cost — broken CI blocks PR merge and requires an unplanned commit, adding session overhead.

**Process patch:**

→ Deferred patch (cannot apply this run — spec document is outside execution engine write scope for non-ST-item changes):
  - File: `docs/testing/risk_dashboard_scenarios.md`
  - Section: §5 Test Infrastructure Preconditions (existing section) or a new §6 Test Maintenance Protocol
  - Change required: Add a note: "When a component's UI microcopy (empty state messages, error text, placeholder text) is changed in a frontend delivery, the Playwright test author must audit SC-RD-* tests for string assertions against that component and update them in the same PR or a follow-on commit before the EPIC merges." This makes the cross-EPIC test maintenance obligation explicit.
  - Owner: Director of Quality
  - Target: Before Sprint 2 Playwright test expansion

### Friction Item 3

**Classification:** Type C — Dependency Stall: The Playwright test scaffold used path-based navigation (`/risk`) that fails under HashRouter; the routing architecture was not documented in the test scaffold.

**Recurrence:** No — first sprint with Playwright tests against this React app.

**What happened:**
The initial SC-RD test suite used `page.goto('/risk')` for navigation. The React app uses `HashRouter`, which routes to `/#/RiskDashboard` — path-based navigation silently loads the wrong page (the main Dashboard). All 17 tests appeared to run but asserted against the Dashboard page's content (e.g., Recharts axis ticks reading "08 Feb" instead of the HeatGauge SVG). The failure was discovered only after the first CI run. The fix (changing to `page.goto('/#/RiskDashboard')`) was straightforward but required diagnosing the mismatch from CI logs and re-running CI.

**Where in the routine:** STEP 3.1.C — ST-11 QA gate; first Playwright CI run.

**Root cause:** Missing artefact — the Playwright test scaffold has no documented note about the app's routing architecture (HashRouter vs BrowserRouter). The engine authored the test without this information, defaulting to the conventional `/path` form. The routing mechanism is not specified in `risk_dashboard.md` or any referenced frontend spec.

**Blast radius analysis:**
- What would have propagated: Any future Playwright test addition would face the same trap unless the developer knew to check HashRouter conventions. The spec has no "Frontend Architecture Notes" section; the test scaffold has no header stating the routing mechanism.
- When it would have surfaced: On the next Playwright test addition to a new page route — next sprint or Sprint 2.
- Recovery cost if uncaught: Low per occurrence (easy fix once identified). Medium discovery cost — HashRouter routing failure is silent (page loads but is wrong), which means failures produce confusing assertion errors rather than "page not found".

**Process patch:**

→ Deferred patch (cannot apply this run — playwright config is outside execution engine write scope for non-ST-item changes):
  - File: `tests/e2e/risk-dashboard.spec.js` (and any future test files)
  - Section: File header comment (lines 1–10)
  - Change required: Add a comment block at the top of every Playwright spec file stating: "Routing: This app uses HashRouter. All navigation must use page.goto('/#/PageKey') — NOT page.goto('/path'). Page keys are defined in src/pages.config.js." This makes the routing architecture explicit to any engineer writing or reading the test.
  - Owner: Director of Quality
  - Target: Before Sprint 2 Playwright test additions
