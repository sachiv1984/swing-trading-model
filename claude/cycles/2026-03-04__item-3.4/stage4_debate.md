## Candidate 1: 3.5 — Alerts & Notifications

### 5.0 Required Case (Product Owner)

1. **Problem:** Users away from desk miss exit recommendations. Position held past stop is the strategy's defined failure mode. Without alerts, the human-in-the-loop model fails at its most critical moment.
2. **Strategy intent served:** §3 — "Exit signals generated by the system are recommendations, not automatic orders." For the recommendation to reach the human, the human must be informed. Alerts are the notification mechanism for §3 to be reliable.
3. **What if we don't:** Position held past stop, uncapped downside. The strategy's protective function is unreliable.
4. **Displacement:** No displacement required — this is an existing roadmap item, not a new addition.

### 5.1 Challenger Counter-Argument

**Challenger position:** Park

**Evidence:** DL-002 (2026-03-01) — "v2.0 pre-alignment may not open until all three are confirmed" — explicitly elevated the QA planning session for notification delivery to a hard gate. The third gate remains uncleared.

**Reason:** DL-002 was written because the async failure modes and notification delivery testing surface were underestimated. The QA planning session is required precisely to scope testing requirements before pre-alignment opens. Re-committing 🔥 without the gate cleared repeats the exact risk DL-002 was written to prevent.

**Consequence:** If pre-alignment opens on this feature without QA planning, notification delivery ships with unaddressed test coverage, creating operational risk in the highest-stakes user notification channel (stop-loss approach).

### 5.2 Product Owner Response

Accept. The QA planning gate must remain active. Product Owner cannot commit 🔥 without it. However, the gate condition is simple to close: a QA planning session for notification delivery must be scheduled and completed before v2.0 pre-alignment opens. This will be recorded as a standing gate condition — once the session is completed, no additional rebalance cycle is required for re-commitment.

**Outcome: 🅿 Park** — QA planning gate open. Gate condition: "QA planning session for notification delivery completed — specify: test types, notification delivery modes, expected test infrastructure." Once closed, 3.5 auto-advances to active v2.0 planning without needing a new rebalance cycle. The rebalance engine records this as a conditional defer with an auto-advance trigger.

## Candidate 2: 4.3 — Signal Exposure Enhancement

### 5.0 Required Case (Product Owner)

1. **Problem:** The signals API already accepts `top_n` and `lookback_days` at the backend, but users cannot control them — fixed at defaults. Users who want a wider or narrower signal window cannot adjust without code changes.
2. **Strategy intent served:** §12.2 — "elements that may change: ATR period, multipliers." SRB confirmed `top_n` and `lookback_days` are display/query controls, not strategy execution parameters. Gate cleared.
3. **What if we don't:** Two documented configurable parameters remain inaccessible. Value of the feature is zero despite backend support existing.
4. **Displacement:** No new displacement — this is a gated item being unblocked, already in v2.0 scope.

### 5.1 Challenger Counter-Argument (Score-4: §13 boundary cited first)

**Challenger position:** Park

**Evidence:** §13.2 — "a multi-strategy or configurable strategy platform" — the specific boundary being approached. The SRB is a point-in-time gate clearance, not a blanket immunity. Scope containment is the enforcement mechanism.

**Reason:** The SRB cleared `top_n` and `lookback_days` as query/display controls. It did NOT authorise the exposure of any other parameters. Once this feature is in active development, pressure will emerge to expose additional parameters (lookback period for ATR, regime thresholds, etc.) believing they're within the cleared scope. Without a PoG document naming the exact two cleared parameters, the implementation team has no mechanical guardrail.

**Consequence:** Next developer or session may add parameters beyond what the SRB cleared, creating a §13 violation that goes undetected until the next SRB review.

### 5.2 Product Owner Response

Rebut. The Challenger's concern is precisely what the PoG mechanism addresses. The PoG issued in STEP 5.3 will name exactly `top_n` and `lookback_days` as the only cleared parameters. This creates the mechanical guardrail the Challenger requests. The SRB decision is explicit: "Parameters must remain query/display controls only. Any future change that allows users to modify signal weights, scoring logic, or ranking methodology would require a new §13 review." The PoG immutably records this. Advance.

**Strategy Rules & System Intent Owner confirmation:** Confirmed. The SRB decision, combined with the PoG, provides adequate protection. The scope boundary is clear. ✅ Advance, contingent on PoG issuance.

**Outcome: ✅ Advance** — PoG required (issued in STEP 5.3 below).

## Candidate 3: IDEA-director-of-quality-20260304-02 — Golden Output Regression Baseline for CI

### 5.0 Required Case (Product Owner)

1. **Problem:** CI gate blocks on crash/non-existence but does not verify numeric correctness. A silently wrong stop calculation passes CI.
2. **Strategy intent:** §11 — "must be consistent across production backtests, live logic, and performance metrics." §14 — "must be explicit, intentional, and owned." Golden baseline makes the spec's numeric rules machine-enforceable.
3. **What if we don't:** Silent calculation regressions reach production. Stop values, position sizes, or P&L could be wrong without any alert.
4. **Displacement:** No roadmap displacement — this is a backlog-level quality item to be added to the backlog and scoped into v1.8 technical work.

### 5.1 Challenger Counter-Argument

**Challenger position:** Park

**Evidence:** §11 — the existing `POST /validate/calculations` with `validation_data.py` already validates 14 critical calculations against expected values. This is already a form of golden output testing.

**Reason:** The marginal value over the existing validation endpoint must be weighed against the risk of two parallel correctness systems diverging. If both exist and conflict, there is no single source of truth.

**Consequence:** Two correctness systems require coordination of expected values; a divergence creates confusion about which is authoritative.

### 5.2 Product Owner Response

Rebut. The Challenger correctly identifies that `validation_data.py` covers analytics metrics. The golden baseline addresses a different layer: position-level stop calculations, trailing stop update logic, and position sizing outputs — which `POST /validate/calculations` does not test. These are complementary systems covering different code paths. The "two systems" concern is valid and addressed in the implementation constraint: golden outputs must explicitly exclude what `validation_data.py` already covers. Advance.

**Outcome: ✅ Advance** — promoted to backlog as high-priority quality item. Implementation constraint: scope to stop/sizing/trailing-stop calculations only; no duplication of existing validation_data.py coverage.

## Candidate 4: IDEA-strategy-owner-20260304-01 — Backtest vs Live Stop Reconciliation Report

### 5.0 Required Case

1. **Problem:** No automated check that live position stops match canonical calculation rules. Drift would be undetected until an incorrect recommendation fires.
2. **Strategy intent:** §7.3 — "Stops must never move downwards. This rule is absolute." §11 — consistency across backtests, live logic. Reconciliation enforces the consistency requirement operationally.
3. **What if we don't:** Stop drift accumulates silently. Position held past correct stop or exited prematurely.
4. **Displacement:** Backlog-level quality item. Implementation dependency: after golden output baseline.

### 5.1 Challenger Counter-Argument

**Challenger position:** Park

**Evidence:** §11 — the golden output baseline (Candidate 3) addresses the same correctness risk via CI. Both ideas address calculation correctness.

**Reason:** If the golden baseline is implemented, CI catches stop regressions before deployment. The reconciliation report catches a different scenario (live data drift) but the marginal value after CI is protected is lower.

**Consequence:** Implementing both doubles maintenance burden for the same risk category; report output may go unactioned if there is no alert or escalation path.

### 5.2 Product Owner Response

Modify. The Challenger identifies a real overlap in the CI dimension. However, the reconciliation addresses retrospective operational drift — a live position corrupted before a fix was deployed, for example. CI is prospective; reconciliation is retrospective. They are complementary, not duplicative. Implementation dependency: after golden baseline. The escalation concern is valid — the implementation must include an alert/escalation path (report to operational log with explicit action required flag). Advance with these constraints.

**Outcome: ✅ Advance** — promoted to backlog. Implementation dependency: after golden output baseline. Constraint: include explicit escalation on discrepancies.

## Candidate 5: IDEA-challenger-20260304-02 — Define and Document the Unavailability Failure Mode

### 5.0 Required Case

1. **Problem:** No policy defines what the user should do when unavailable for 24-48 hours during an active stop recommendation. Position held past stop is real financial exposure.
2. **Strategy intent:** §3 — "Entries and exits are executed manually." §13.1 — "human-in-the-loop by design." The failure mode of human unavailability is undocumented.
3. **What if we don't:** Users have no procedure. Financial exposure continues undocumented.
4. **Displacement:** Policy documentation task (~0.5 day). No roadmap displacement.

### 5.1 Challenger Counter-Argument

**Challenger position:** Park

**Evidence:** §13.1 — "human-in-the-loop by design" is a design decision, not a gap. §13.2 — the system "is not an automated trading bot." Documenting broker-level workarounds is outside system scope.

**Reason:** Creating an operations guide for system limitations could set precedent for documenting other limitations (network outages, broker downtime). The system cannot help users who are unavailable — it can only inform. The policy is more appropriately user education than product governance.

**Consequence:** An operational guide for broker-level workarounds may create expectation of future broker API integration (explicitly out of scope).

### 5.2 Product Owner Response

Rebut. The Challenger's scope concern is narrow. The proposed output is a single policy statement — not a guide to broker workarounds. It says: "Before any planned unavailability exceeding X hours, ensure a hard stop order is placed at broker at the current trailing stop price." This is safety guidance, analogous to documenting "what to do in a power outage" in any safety-critical system. It does not extend the system boundary or imply automation. The financial risk of undocumented behaviour is real. Advance.

**Outcome: ✅ Advance** — promoted to backlog as policy documentation task.
