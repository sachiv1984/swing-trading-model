### Friction Item 1

**Classification:** Type A — Governance Drift: A documented rule was ignored — EPIC branch requirement and commit format were bypassed.

**Recurrence:** No — v1.7 sprint had no frontend delegations; this is the first cycle with a Base44 delegation.

**What happened:**
ST-03 (Frontend: Risk Dashboard Page Implementation) was committed directly to `main` by the Base44 Frontend Prompt Owner across 8 commits (2026-03-05), bypassing the designated EPIC branch `exec/2026-03-04__release-v1.8/EPIC-01` and not using the `[EPIC-01][ST-03]` commit format. No PR was opened. The engine raised ESC-EXEC-20260305-02; Product Owner accepted the breach and accepted all 8 resulting deviations. The breach was not malicious — the delegation record (DEL-20260305-02) did not include a "Target branch" field specifying where commits must go, leaving the assignee without an explicit instruction on branch governance.

**Where in the routine:** STEP 3.1.B — delegated_frontend unblock detection; branch and commit format verification.

**Root cause:** Template omission — the delegation record template in `claude/agents/base44_frontend_prompt_owner.md` does not include a "Target branch" field. The commit format requirement is listed, but without the branch name, the assignee has no concrete instruction to follow.

**Blast radius analysis:**
- What would have propagated: Any future frontend delegation using the same template will face the same gap. Repeated branch governance breaches undermine PR-per-EPIC structure, CI check integrity (quality_gate.yml, governance_sync.yml), and traceability.
- When it would have surfaced: On the next `delegated_frontend` item — next sprint.
- Recovery cost if uncaught: Medium — each recurrence requires a PO escalation and deviation acceptance; repeated breaches erode the PR review gate.

**Process patch:**

→ Deferred patch (cannot apply this run — `claude/agents/` is outside execution engine write scope):
  - File: `claude/agents/base44_frontend_prompt_owner.md`
  - Section: §3 — Delegation Record Template (or the "What is needed" field specification)
  - Change required: Add a mandatory "Target branch" field to the delegation record template with the value `exec/<cycle_id>/EPIC-xx` — placed immediately after the "Branch" field in the delegation record format so the assignee sees the target branch before reading the commit format requirement.
  - Owner: Head of Specs Team
  - Target: Before next sprint with a delegated_frontend item

### Friction Item 2

**Classification:** Type A — Governance Drift: The `governance_sync.yml` workflow used a string identifier where a numeric issue number was required, causing CI check failures on legitimate merges.

**Recurrence:** No — this is the first cycle where `governance_sync.yml` was exercised under real branch conditions.

**What happened:**
When commits with `[EPIC-xx][ST-xx]` format were pushed to exec branches, `governance_sync.yml` attempted to call `gh issue close` with the string `ST-xx` as the issue identifier. The `gh` CLI requires a numeric issue number or URL; the call failed with `invalid issue format`, causing the `sync_state` CI check to fail on PRs #29 and #30. Additionally, the `--comment` flag on `gh issue close` fails because the GitHub token lacks `issues:write` scope for comments. The engine fixed the numeric ID lookup at ESC-EXEC-20260305-01 resolution (replaced the literal string with a `gh issue list --search` lookup). The `--comment` flag issue was identified but not fixed within the sprint.

**Where in the routine:** STEP 3.1.A step 5 — push to exec branch triggers governance_sync.yml CI check.

**Root cause:** The workflow was authored without being tested end-to-end against a real exec branch push with real GitHub issues. Two defects were present simultaneously: wrong argument type for `gh issue close`, and an unsupported flag for the token's permission scope.

**Blast radius analysis:**
- What would have propagated: Every future exec branch push triggers `sync_state`; if the remaining `--comment` defect is not fixed, CI will show a failed check on every PR. Over time, teams normalise "ignoring the sync_state check", undermining the gate.
- When it would have surfaced: On the next exec branch push to GitHub.
- Recovery cost if uncaught: Low per occurrence (ignored check) but high governance cost — normalised CI failures degrade confidence in all CI signals.

**Process patch:**

→ Deferred patch (cannot apply this run — `.github/workflows/` is outside execution engine write scope):
  - File: `.github/workflows/governance_sync.yml`
  - Section: "Update State and Close Issue" step — the `gh issue close` call
  - Change required: Remove the `--comment "..."` flag from the `gh issue close` invocation (the flag fails because the GitHub Actions token lacks issues:write comment scope); close without comment — issue closure alone is sufficient governance signal.
  - Owner: Infrastructure & Operations Owner
  - Target: Before next sprint execution (next exec branch push)

### Friction Item 3

**Classification:** Type C — Dependency Stall: A pre-condition for scenario execution (test data injection) was invisible at planning time and not discovered until QA attempted to execute the scenarios.

**Recurrence:** No — first sprint with a formal QA scenario document.

**What happened:**
The Director of Quality authored 27 acceptance scenarios in `docs/testing/risk_dashboard_scenarios.md` v1.0.1 covering the full Risk Dashboard spec. During execution (ESC-EXEC-20260305-03), it emerged that 17 of 27 scenarios (Groups A, B, C, D, F) require specific portfolio states or position combinations that cannot be achieved in the current environment without a test data injection mechanism. Only 10 scenarios (Group E — prospective heat, which uses live API inputs) were executable. The 17 unexecutable scenarios were not a quality failure — they were a test infrastructure gap. The QA sign-off was given on the 10 executable scenarios plus code review of HeatGauge logic.

**Where in the routine:** STEP 3.1.C and ESC-EXEC-20260305-03 — QA scenario execution gate.

**Root cause:** Missing artefact — the scenario document (`docs/testing/risk_dashboard_scenarios.md`) has no "test infrastructure preconditions" section. Scenarios were authored against the spec without documenting what environment state is required to execute them. The gap was invisible until execution was attempted.

**Blast radius analysis:**
- What would have propagated: The 17 unexecutable scenarios remain unanswered for v1.8. Any future sprint touching the Risk Dashboard spec sections covered by these scenarios will face the same execution gap unless infrastructure is built. Test coverage confidence is overstated.
- When it would have surfaced: At next QA execution attempt against the same spec sections — or silently, if execution is not attempted again.
- Recovery cost if uncaught: Medium — test infrastructure gap requires a dedicated backlog item and potentially a backend endpoint for test data injection; scenarios are valid but unexecutable until then.

**Process patch:**

→ Deferred patch (cannot apply this run — `docs/testing/` is outside execution engine write scope for non-ST-item changes):
  - File: `docs/testing/risk_dashboard_scenarios.md`
  - Section: New section — "Test Infrastructure Preconditions" (to be added before the scenario groups)
  - Change required: Add a "Test Infrastructure Preconditions" section listing: (a) which scenario groups require test data injection, (b) what portfolio state each group requires, (c) current status of that infrastructure (not built), (d) which scenarios are executable in a production environment without special state. This makes the gap visible before QA attempts execution.
  - Owner: Director of Quality
  - Target: Before next sprint touching Risk Dashboard spec sections

### Friction Item 4

**Classification:** Type D — Cognitive Fatigue: Session terminated after recording EPIC-02 QA sign-off but before the user reported the EPIC-02 PR merge; sprint close was never triggered.

**Recurrence:** Yes — appeared in 2026-03-02__release-v1.7 as EX-LL-03 ("lessons_learnt_execution.md not created at sprint close"). Prior outstanding action: "always invoke run sprint as the explicit entry point." That action was implemented — but the underlying issue (sprint close not completing before session ends) recurred with a different root cause.

**What happened:**
The execution engine was formally invoked and ran all sprint work correctly. EPIC-02 was QA-signed-off and PR #32 was opened. The session ended after commit `294e459` (recording EPIC-02 QA sign-off and CyberSec acknowledgement). The user then merged PR #32 on GitHub, but the engine was not re-invoked to record the merge, update `execution_state.json`, and trigger STEP 5 (Sprint Close). As a result: `sprint_close.md` was never created, `execution_state.json` remained unsealed with `pr_status: "open"` for EPIC-02, and `lessons_learnt_execution.md` was not filed. The next session attempted `run delivery verification`, which failed preflight because these artefacts were absent.

**Where in the routine:** STEP 4 (Merge Gate) and STEP 5 (Sprint Close) — gap between PR merge on GitHub and engine recording the merge.

**Root cause:** Process gap — the execution engine depends on the user explicitly re-invoking `run sprint` after each PR merge so it can update state and check for sprint close readiness. There is no mechanism to prompt or remind the user to do this. When a session ends mid-sprint, the burden of re-invocation is invisible.

**Blast radius analysis:**
- What would have propagated: Every sprint that spans multiple sessions faces the same risk. If the user moves directly to `run delivery verification` after all PRs are merged (as happened here), the preflight fails and a reconstruction run is required — adding delay and risk of artefact gaps.
- When it would have surfaced: At `run delivery verification` preflight — sprint_close.md absent triggers a hard gate failure.
- Recovery cost if uncaught: Low-to-medium — sprint close can be reconstructed from execution_state.json and git history, as done this run. But it adds session overhead and risks completeness gaps.

**Process patch:**

→ Deferred patch:
  - File: `claude/system/sprint_planning_prompt.md`
  - Section: §5 or a new "Sprint Close Reminder" section — alternatively, add to the execution prompt STEP 4 output
  - Change required: Add a user-facing note in the execution engine's merge gate output (STEP 4 completion message) that explicitly states: "Re-invoke `run sprint --cycle <cycle_id>` after each subsequent EPIC merge so the engine can update state and check for sprint close." This makes the re-invocation requirement explicit and visible at the moment it matters.
  - Owner: Head of Specs Team
  - Target: Before next sprint execution

### Friction Item 5

**Classification:** Type C — Dependency Stall: No pre-sprint vulnerability scan was performed during planning; a known CVE in `requests` (upgraded as part of ST-07) was present in the codebase entering the sprint.

**Recurrence:** No — first sprint with formal dependency scanning.

**What happened:**
ST-07 introduced `pip-audit` as a CI gate. During implementation, a CVE was found in the `requests` package and the dependency was upgraded. This CVE was pre-existing at sprint start and would have been present across the entire sprint duration. Had the sprint included a different EPIC that triggered a PR before EPIC-02 was merged, the CVE scan would have blocked that merge unexpectedly. The issue was resolved within the sprint scope, but it was reactive rather than proactive.

**Where in the routine:** STEP 0 — sprint initialisation; pre-condition validation.

**Root cause:** Process gap — the release planning prompt (`sprint_planning_prompt.md`) does not include a pre-sprint dependency health check. Vulnerability status is not verified before sprint scope is locked.

**Blast radius analysis:**
- What would have propagated: In a sprint where the vulnerability scan CI gate is active but the dependency fix is in a late EPIC, all earlier EPIC PRs could be blocked unexpectedly by a CVE that was present but undiscovered at planning time.
- When it would have surfaced: At merge gate for any EPIC PR after the vulnerability scan CI is active — an unexpected CVE block mid-sprint.
- Recovery cost if uncaught: Medium — unblocking requires either upgrading the dependency (if simple) or obtaining a risk acceptance. Discovering it at merge gate adds latency and potential delivery pressure.

**Process patch:**

→ Deferred patch:
  - File: `claude/system/sprint_planning_prompt.md`
  - Section: STEP -1 (Preflight) or a new pre-sprint health check step
  - Change required: Add a pre-sprint pip-audit check step: before sprint backlog is locked, run `pip-audit` against `backend/requirements.txt` and report findings. High/critical CVEs must be either resolved before sprint start or explicitly accepted (with backlog item) as a known risk. This surfaces the vulnerability landscape before scope is sealed.
  - Owner: Head of Specs Team
  - Target: Before next sprint planning run
